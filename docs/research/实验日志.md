# SkillScope 实验日志

## 2026-08-17：研究启动与环境审计

### 目标变更

研究目标从讨论设计扩展为：完成 SkillScope 可行性实验、依据证据迭代设计，并开发可运行的 Pi 插件。新增要求是所有步骤、实验假设、失败和决策均以 Markdown 留档。

### Step 1：仓库审计

- 仓库初始仅含两份 v0.1 设计文档、README、LICENSE 与 `.gitignore`；尚无代码。
- Git 分支为 `main`，启动时与 `origin/main` 同步。
- Node `v26.0.0`，Python `3.9.6`。

结论：需要从零建立插件与实验 Harness，但不存在需要兼容的现有实现。

### Step 2：密钥可用性检查

- 非交互 shell 未直接继承 `EXPERIMENT_KEY`。
- 交互式 `zsh -ilc` 能读取变量；变量引用存在于本机 `.zshrc`。
- 日志只记录 `set/missing`，未输出密钥值。

结论：真实实验命令必须通过交互式 zsh 启动，或由调用进程显式继承环境；禁止把密钥复制到 `.env`。

### Step 3：Zen API 模型发现

- 请求：`GET https://opencode.ai/zen/go/v1/models`。
- HTTP：`200`。
- 返回模型包括 `gpt-5.6-luna`、`qwen3.7-plus`、`glm-5.2`、`kimi-k3`、`deepseek-v4-flash` 等。

下一步：使用一个最小函数工具探测 `/chat/completions`、tool call 格式、usage 和错误语义；模型先选 `gpt-5.6-luna` 做快速 Pilot，必要时加入第二模型验证外部有效性。

### Step 4：Pi 包与官方 API 核验

- npm 确认 `@earendil-works/pi-coding-agent@0.84.2` 存在。
- 官方 SDK 文档确认 `createAgentSession`、`SessionManager.inMemory`、`SettingsManager.inMemory`、工具 allowlist、自定义工具、订阅、abort/dispose。
- 官方 Extension 文档确认 `registerTool`、工具覆盖/操作后端以及 `terminate: true` 结构化终止工具。
- 官方安全说明再次确认 Pi 进程内运行不构成 OS 沙箱。

异常记录：第一次 API 模型发现脚本使用了 zsh 只读变量名 `status`，命令在发出网络请求前后的状态处理处失败；改名为 `experiment_http_code` 后成功。以后脚本变量统一使用 `experiment_` 前缀。

下一步：下载并检查 0.84.2 的真实类型定义；实现最小 Pi 嵌套 Session Spike，而不是只依赖文档示意代码。

### Step 5：Pi Package 工程骨架

- 新建 `package.json`，包名 `pi-scoped-skills`，版本 `0.1.0`。
- Pi manifest 直接加载 `src/pi/index.ts` 与 `skills/`；官方包文档确认 Pi 可直接加载 TypeScript Extension。
- Pi 自带核心包通过 `peerDependencies: "*"` 声明，遵循官方包规则；开发环境同时精确固定 `@earendil-works/pi-coding-agent@0.84.2`。
- TypeScript、Node 类型、TypeBox 与 YAML 均锁定精确版本；`.npmrc` 开启 `save-exact`。
- 实验代码不包含在 npm `files` 白名单中，避免发布包携带原始实验结果或 Canary。

假设：Extension 直接分发 TypeScript 比预编译 dist 更贴近 Pi 官方包机制，并能避免源码/构建产物漂移。该假设仍需通过本地 `pi -e .` 和打包 smoke test 验证。

### Step 6：Zen 单模型能力探测与假设推翻

- 官方 Go 模型表将 `gpt-5.6-luna` 映射到 `/responses`，而不是 `/chat/completions`。
- Luna 在 Chat 路由返回非 2xx 的空 completion 外壳；使用正确 Responses 路由后明确返回当前区域不可用的 HTTP 403。
- 同一密钥、网络和 Bearer 鉴权下，`glm-5.1` 的普通响应、强制函数调用、工具结果续接、usage、`temperature` 和 `seed` 均得到 HTTP 200。
- `glm-5.1` 在过小 `max_tokens` 下可能只产生 `reasoning_content` 并以 `finish_reason: length` 结束，空 `content` 不能当成成功。

被推翻的假设：不能根据 `/models` 列表假定所有模型共享 OpenAI Chat Completions 契约，也不能根据 JSON 外壳判定请求成功。

设计修正：Runner 必须验证 HTTP 2xx、合法终止原因和可消费内容，并将 transport 错误、区域不可用、鉴权失败与 Token 预算耗尽分类。完整请求形状与脱敏观察见 `docs/research/Zen_API_探测.md`。

### Step 7：主实验模型约束更新

用户明确指定 `deepseek-v4-flash`，原因是其可用额度更高。因此：

- 真实访问边界矩阵和 Pi 端到端运行均以 `deepseek-v4-flash` 为主模型；
- `glm-5.1` 仅保留为证明密钥、Bearer 鉴权和 Chat Completions 工具链路可用的控制证据；
- 不因额度较高就假定契约相同。正式矩阵前单独验证 transport、工具调用续接、usage、取样字段和足够的输出预算。

Preflight 结果：`deepseek-v4-flash` 的官方与实测 transport 均为 `/chat/completions`；普通回答、forced tool call、使用服务端真实 call ID 的 tool-result 续接和 usage 全部通过。`temperature: 0` 与无符号整数 seed 被真实解析，但本轮不声称 seed 保证确定性。未知顶层字段被服务端静默接受，因此 Runner 不能依赖远端做请求 Schema 验证。冻结建议为 `max_tokens=1024`，仅在 `finish_reason=length` 时以 2048 完整重跑该次 Scope 一次。

### Step 8：Pi 0.84.2 动态 Provider 认证桥真实运行

先在临时工程中完成精确版本编译和确定性 faux-provider 测试，再从交互式 shell 继承 `EXPERIMENT_KEY`，使用 `deepseek-v4-flash` 运行真实子 Session。桥接步骤仅使用 Pi 公开 API：

1. 父侧 `ModelRegistry` 注册 Zen Chat Completions provider；
2. 新建不读 `models.json` 的子 `ModelRuntime`；
3. 克隆 provider config，将父侧解析后的 API key 仅写入子运行时内存 CredentialStore；
4. 调用 `runtime.refresh({providers:[id], allowNetwork:false})`，修复 0.84.2 在动态注册后暂时过期的 auth/availability snapshot；
5. 以新的 `SessionManager.inMemory()` 创建子 AgentSession。

首次真实请求在 5.6 秒内退出 0，脱敏断言为：`dynamicProviderCloned=true`、`apiKeyResolved=true`、`childAuthConfigured=true`、`toolCalls=1`、`completionResults=1`、`assistantMessages=1`、`lastRole=toolResult`。随后发现 `ModelRuntime.create({modelsPath:null})` 默认仍可读全局 auth storage，于是把子运行时改成显式公开 `InMemoryCredentialStore`，在更严格版本上重新编译并真实运行：12.9 秒退出 0，所有断言不变。这证明独立 Pi Session、真实 Zen 模型、短命内存凭据、结构化工具与 `terminate:true` 链路可行。该证据仍不替代完整插件包加载、资源网关和 Trace 的端到端验证。运行输出未包含密钥，密钥未写入仓库。

### Step 10：实验实现独立审计（正式运行前）

审计发现并暂停真实矩阵的阻断项：

- Canary 由 job ID 确定派生，不是每次执行 fresh random；
- 只脱敏 payload，其他 result/planner/request/error 字段可保留模型复述的 Canary；
- provider 错误可被误计为能力失败；
- 证据 provenance 只到路径级，list、无命中 search 或读错行后仍可猜行号通过；
- 运行既有 manifest 时可静默替换模型，job ID 未包含完整 config；
- JSONL 崩溃尾行不可恢复，manifest 不是原子写；
- worker 可看到 `ORACLE/INFERRED/NEED_RESOURCE` 内部臂名，引入标签启发偏差；
- 本地结果、资源请求和 planner validator 未严格拒绝额外字段；
- 动态资源请求的路径包含判定未先拒绝 `..` 等非法路径。

决策：上述项目修复且 mock/hostile 回归全绿前，不运行 14×5×3 真实矩阵。这些失败作为研究过程保留，不从记录中删除。

### Step 11：完整 Pi Extension + 真实模型端到端验证

新增 `experiments/pi-e2e/run-live.mjs`，验证的不是孤立 SDK 调用，而是 Pi Extension 实际注册的 `scoped_skill_run`：外层以最小 Pi API 宿主确定性调用工具，插件再创建独立子 Session，通过 Core Resource Gateway 读取一个被授权的合成故障日志，并将 Trace 写到项目外临时目录。模型固定为 `opencode-go/deepseek-v4-flash`，凭据仅从交互式登录 shell 的 `EXPERIMENT_KEY` 进入短命内存 CredentialStore。

第一次运行在网络请求前失败：Node 在 TypeScript loader 的副作用生效前静态链接了 `src/pi/index.ts`，报 `ERR_MODULE_NOT_FOUND`。将插件入口改成 loader 安装后的动态 `import()` 后，第二次又暴露脚本自身的 TDZ：`EphemeralCredentialStore` class 在声明前被实例化。将它改成可提升的函数构造器后再跑。两次失败均属于 E2E 驱动脚本，不是模型或插件能力失败。

第三次运行退出 0：

- 状态：`SUCCESS`；
- 墙钟时间：15,171.54 ms；
- 模型报告 usage：3 turns、3 tool calls、8,307 total tokens；
- 输出准确识别 schema v3/v2 不匹配，并给出将 producer 暂时 pin 到 v2 的直接补救；
- `logs/import.log` 同时出现在 actual-read 与 model-visible 集合；
- 未授权的 `private/out-of-grant.txt` 不在 attempted、actual-read 或 model-visible 集合；
- 外部 Trace 的 manifest/events/result 三件套可读且与返回 scope 一致；
- 持久化的实验摘要不包含 API key。

脱敏结果在 `experiments/pi-e2e/results/latest.json`。这证明当前原型的“Pi 工具注册 → 独立 Session → 真实 DeepSeek 工具调用 → 边界受控读取 → 结构化完成 → 外部 Trace”主链可执行；它尚不证明恶意 Extension 的 OS 隔离，也不替代独立审计指出的 Trace 内容策略、端到端 deadline、重复 completion 与 evidence provenance 修复。

### Step 13：70-job 工程 dry pilot 与实验契约证伪

本轮先通过当时版本的本地门禁：runner/audit 29 pass、0 fail、1 个明确的多进程 TODO；fixture lint 为 14 tasks/7 pairs；五条件 scripted smoke 全绿。随后创建 `access-frontier.v1`、14 tasks × 5 conditions × 1 repeat 的 manifest，并以单 runner 进程、并发 4、`deepseek-v4-flash` 完整执行 70/70 jobs。

运行完成后的机械结果：

- 60 `completed`，10 个模型/协议内生失败：4 `MAX_TOOL_CALLS`、5 `INVALID_RESULT`、1 `MISSING_CONTROL_CALL`；
- 0 provider、network 或 harness failure；
- 70/70 `policyPass`；四个受限条件 0/56 Canary model-visible，而 `PROJECT_READ_ONLY` 因授权整个项目为 14/14 model-visible；最终结果 0/70 exfiltrated，原始 JSONL 未发现未脱敏 Canary token；
- 五个条件的 `semanticPass` 与 `hardPass` 均为 0/14；
- 60 个有合法 submission 的结果全部 `FACTS_MISMATCH`；其中项目/Oracle/Inferred/Need 的证据 provenance 大多或全部通过，说明失败集中在答案命名契约，而不是访问证据不足；
- NEED 条件 0/14 发出 resource request，因此本轮不能估计动态补权恢复率。

人工抽查推翻了“精确 code/facts 是客观 validator”这一假设。Worker 只看到自由的 `answerCode: string` 和 `facts: object`，却被隐藏 validator 按作者私有命名精确评分。例如语义正确的 `RETRY_LIMIT_ZERO` 会因隐藏答案写成 `RETRY_DISABLED` 而失败；snake_case 对 camelCase、增加一个正确事实字段也会失败。这个目标对模型不可识别，故 0% 不能解释为模型或 SkillScope 能力为零。

运行期间的并行审计还发现三项可复现性问题：v1 manifest 没有真正冻结 `apiBase`；provider retry 分支存在一个仅重试时触发的 `usage` 未定义错误；源码在运行进程加载后继续演化，manifest 又没有 implementation revision。虽然该进程使用启动时已加载、当时门禁全绿的模块并完整退出 0，本批仍降级为 **engineering dry pilot**，不得进入正式架构映射。

设计修正：

1. 每个任务公开一个不泄露真值的 response contract：至少两个合理 `answerCode` 候选，以及 exact facts 字段、类型/值域；隐藏 expected answer 必须通过同一契约。
2. 自然五臂继续报告 NEED 的实际触发率；另建 forced-undergrant 机制实验，配对比较“确定缺证据且不能补权”与“同样初始缺证据但允许一次 typed request + fresh rerun”，不得把强制 miss 冒充自然 planner 效果。
3. endpoint、provider protocol、模型与完整 config 全部进入 manifest/job identity；协议提升后重建 manifest。
4. 可信 Pilot 只从已提交、工作树不变的实现 revision 启动；启动/结束 revision、manifest hash 与门禁结果写入日志。
5. 当前分析器中的 5pp 非劣界限不是 v1 预注册内容，只能标为探索性 post-hoc decision aid。下一次确认性实验必须在开跑前另行冻结阈值、最小任务数与停止规则。

这一轮的价值不是给出条件排名，而是用真实 API 提前否决了一个会把所有能力比较归零的测量设计，并证明 Canary/访问政策通道与语义 validator 必须分开观察。

本地原始 dry-run artifact 均为 70 行，已由 `.gitignore` 排除，避免把隐藏 fixture truth 与未审阅模型正文顺手提交。复核用摘要：manifest SHA-256 `ae3d03eba1c152f1b732bb9b3fc147e1848887b84319ee8256bb274a625020ec`；results SHA-256 `7e5d685f2a2b1e1c7a2e27aa6e969986f86c4e44c4fc9b5d1286d2a314c4d266`。

随后尝试用修订后的正式 analyzer 读取 v1 dry manifest，命令按设计退出 2，并逐行报告 `manifest job is missing frozen apiBase`。没有为得到图表而绕过该检查；本轮诊断数字由只读机械聚合取得，正式 analyzer 的 fail-closed 行为本身也作为 endpoint 身份修复的回归证据。

### Step 16：公开 response contract、Prompt 源行与独立补权机制修正

### Step 31：首个组合拓扑真实preflight暴露upstream输入投影缺口

Clean baseline `c2957e1392b5db5a2a5e73c02d5dc94d47648e55` 的四条件工程preflight是首次真实任务API调用，不进入72-job效果数据。Parallel按预期形成两个重叠child Scope并合法abstain；三个串行条件的方向与时序都正确，但第二个child均在模型turn前`INVALID_INPUT`。Matched与Adaptive因此未达到预期Hard Pass；所有trial仍started=disposed=3、active=0，父Sentinel均未命中。

### Step 32：第二个组合preflight暴露“优化掉边”与非法补权请求
