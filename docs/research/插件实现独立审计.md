## 1. 结论

冻结快照上，没有发现阻止一个**窄化、单并发、受控文本 fixture、精确文件 BOUNDED grant** 的真实 E2E smoke 的已知源码级阻断项。`promptRefs` 与 `resourceGrants` 已分离；预算只能缩小；child 使用全新内存 Session，不继承父历史或 ambient extensions/context；completion、evidence、`NEED_CONTEXT`、timeout、Trace 和 npm tarball 装载的关键语义都有本地回归证据。

这个结论是有条件的。正式开跑前仍必须完成一次使用已安装 tarball、真实父 Pi 会话和 `deepseek-v4-flash` 的在线 preflight。本审计刻意没有使用密钥，因此只证明了 Pi `0.84.2` 下的离线桥接形状和 fail-closed 行为，没有证明当前账户、provider 配置、endpoint 和模型服务的在线可用性。

以下更强主张仍然不成立：

- 插件不是 OS sandbox；它只是同进程内的模型可见性和工具能力隔离。
- 通用 provider/OAuth/native stream 兼容尚未实现；当前只支持显式 API key 的 OpenAI-compatible chat-completions 路径。
- 对敌对并发文件系统写入没有 fd-relative/openat 级保证，hardlink/mount 语义也没有封闭。
- provenance 目前证明“某资源在 completion 前可见”，不能自动证明 locator、claim 或答案在语义上受到该证据支持。
- 没有全局并发上限或 active-session shutdown registry，不应据此放行生产负载。

因此，本审计给出的判断是：

## 3. 核心边界结论

### 3.1 PromptRef、grant 与预算

父工具 schema 在 `src/pi/index.ts:63-71` 把 `promptRefs` 和 `resourceGrants` 定义为两个字段。Gateway 只把 PromptRef 物化成 child 启动快照；BOUNDED exploration 则只从 grant 建立工具授权。SEALED 下即使提供宽 grant，resource tools 也不会暴露；file PromptRef 的内容仍可在启动时可见。

`src/pi/runtime.ts:354-363` 对 budget override 逐项取声明上限与 override 的最小值。promptRefs 序列化大小、最终 materialized prompt、CompletionPayload 大小、turn、resource tool call 和全生命周期 timeout 均有门禁。`scope_complete` 是控制调用，不计为 resource tool call；研究指标必须按这个定义解释 `toolCalls`。

### 3.2 Fresh child 与最小 loader

`src/pi/pi-backend.ts:95-135` 使用内存 settings、`SessionManager.inMemory(request.cwd)` 和 fresh AgentSession。没有任何父消息传入。`createMinimalResourceLoader` 在 `src/pi/pi-backend.ts:347-364` 返回空 extensions、skills、prompts、themes、AGENTS files 和 append system prompt，只提供固定的最小 system prompt。`noTools: "all"` 后再显式注册经过交集过滤的 `scope_*` 与 `scope_complete`。

这证明的是 child 上下文隔离，不是插件进程隔离。受信任的插件代码仍拥有父 Node 进程的文件、环境和网络权限。

### 3.3 `deepseek-v4-flash` 的 ModelRegistry 桥

`src/pi/pi-backend.ts:221-277` 当前采取窄而明确的桥：

1. 父 session 必须已选模型，且模型 API 必须是 `openai-completions`；
2. OAuth、native provider 和 custom `streamSimple` 明确拒绝；
3. 通过父 `ModelRegistry.getApiKeyAndHeaders(model)` 解析一次认证；没有显式 API key 即拒绝，即使 child 环境中存在同名 ambient key；
4. key 仅写入新建的内存 `EphemeralCredentialStore`，child `ModelRuntime` 使用 `modelsPath: null`、`refreshOnCreate: false`；
5. 注册父模型的 base URL、兼容字段和合并 headers，执行离线 provider refresh；
6. refresh 后检查错误、`hasConfiguredAuth`，再读取 child auth 并要求 key 与父快照严格相等。

独立测试按 `https://opencode.ai/zen/go/v1`、`openai-completions` 和模型 ID `deepseek-v4-flash` 构造了离线 Zen 形状，使用的只是占位 key，没有网络请求。

这不是“克隆任意 ModelRegistry”。父会话必须在正式运行前明确选择 `deepseek-v4-flash`，并通过上述 API-key 路径。认证解析发生在父 Registry 内部，其实现不是本插件控制的；内存 key 也只能等待 GC，没有确定性 zeroization 或 child ModelRuntime dispose API。

### 3.4 Completion、状态与 provenance

`scope_complete` 只接受业务字段：status、summary、data、evidenceRefs、requestedResources、warnings。scope/invocation ID、Skill 版本、时间、usage、Trace ID 和错误归类由 Runtime 生成。

冻结语义如下：

- SUCCESS/PARTIAL 必须给出 data，并按 Skill outputSchema 校验；
- NEED_CONTEXT/BLOCKED 可以省略 data；
- NEED_CONTEXT 必须给出非空 requestedResources；其余状态不得给出 requestedResources；
- requested path 必须是无 absolute、drive prefix、backslash、NUL、`..` 的项目相对路径；operation 必须是 Skill policy 子集且不重复；
- 所有层级名为 `evidenceIds` 的字符串数组，其 ID 都必须存在于 top-level evidenceRefs；
- evidence resource 必须来自 PromptRef，或已进入 completion 前冻结的 `modelVisibleSet`；
- first accepted completion 胜出，第二次 completion 令整个结果 INVALID_RESULT；
- 同一 assistant 消息中的 `scope_read` 与 `scope_complete` 不会制造假 provenance：completion 被非致命拒绝，模型必须在下一 turn 观察 tool result 后重新提交。

真实 Pi faux provider 回归验证了最后一项的事件时序。保留边界是：当前 ledger 是资源级而不是 claim/span 级。一次 `scope_list` 可使路径进入模型可见集合；这足以证明模型见过名字，却不能证明它见过正文。locator 与 claim 文本也没有本地 entailment 检验。因此正式实验必须另有隐藏真值/证据 span validator，不能把插件的 evidenceRefs 校验直接当作答案正确性。

### 3.5 Timeout、abort、budget 与并发

backend timer 在 gateway 物化前启动。gateway、PromptRef 物化、ModelRuntime factory、session 创建和 prompt 执行都与 lifecycle AbortSignal 竞争；晚创建的 session 会 abort/dispose。父取消、timeout 和 budget 在返回时优先于已经出现的 completion。

仍有三类运行限制：

- 同步 CPU 工作会阻塞 Node event loop，因此定时器不是抢占式 CPU 上限；
- 不服从 AbortSignal 的外部 Promise 可能在本次调用返回后继续完成；
- 父工具声明 `executionMode: "parallel"`，但 Runtime 没有 semaphore、队列或 active-session registry，shutdown 也不能遍历并中止所有在途 child。

正式 Pilot 应固定 concurrency=1。任何生产并发放行都应先增加容量上限、内存压力测试和 shutdown/cancel soak test。

## 4. 真实文件系统授权

当前 adapter 先做 lexical containment，再对既存路径执行 `realpath` containment；显式 symlink root 被拒绝，PROJECT walk 跳过文件和目录 symlink。安全 corpus 覆盖 traversal、absolute、drive、separator、prefix collision 和真实 symlink escape。

list-only 目录 grant 只把文件名物化到 virtual Broker，不读正文；当 grant 含 read/search 时，adapter 会预先读取授权 envelope，并在 `physicalMaterializedSet` 中单独记录。它与 Broker 的 `actualReadSet`、`modelVisibleSet` 不是同一概念。

以下限制阻止更强安全主张：

1. `realpath → stat → readFile` 是分离的 check/use 操作；敌对并发写入者可在其间替换路径。需要 fd-relative walk、`openat`/`O_NOFOLLOW`、打开后 `fstat`，或进程/容器后端。
2. 路径 containment 无法表达 inode 来源。独立回归创建项目内 hardlink 指向项目外文件的同一 inode，当前 grant 可以读取该 alias。mount/bind alias 也没有单独策略。
3. 这是同进程 snapshot，不是内核强制边界；插件自身或同进程依赖不受 Broker 限制。
4. read/search 目录 grant 和 PROJECT 会先把整个授权 envelope 的正文加载到进程内，即使模型最终没调用工具；它不是 physical-minimal access。
5. 单文件上限 2 MiB、总量 32 MiB、文件数 5,000；read/search envelope 中任何超限或含 NUL 的文件会使整个 snapshot 失败。PROJECT 在普通仓库上可能很脆弱。
6. PROJECT 默认排除 `.git`、`.pi`、`node_modules`，但不排除 `.env`。只能用于已信任项目，不得用于首次正式实验门禁。
7. Pi adapter 的实际工具面已按 allowedOperations 过滤，但底层 Broker 的 PROJECT `grantedSet` 仍会报告 read/list/search 全集。审计消费者不能单独用该字段推断“模型可调用的 operation”；应结合 Skill policy 和 actual tool surface。
8. real gateway 给 Broker 的 canaries 目前是空数组。插件依靠 visibility ledger 和外部研究 harness，而不是 Broker canary token 检测。

首轮真实 E2E 应使用小型、受控、UTF-8 文本 fixture 和 exact-file BOUNDED grant，不应使用 PROJECT 或宽目录 read/search。

## 5. Trace 与敏感内容

Trace root 必须是项目外绝对路径。创建前会 canonicalize 最近存在祖先，创建后再次 realpath 检查；scope 目录拒绝覆盖和 symlink escape。目录模式为 0700，文件模式为 0600。

`metadata-only-v1` 不落盘 prompt、input、summary、data、evidence、requested resources、warning、error message、路径、可见来源等原文；这些内容只保留 SHA-256、字节数、计数和有限的安全枚举。独立 sentinel 测试覆盖了 prompt/result 和 path-like 字符串，原 marker 未进入 manifest/result。认证 key 从未传给 Trace。

保留限制：

- SHA-256 没有加盐。相同内容可跨 Trace 关联，低熵值可能被字典猜测；metadata-only 不是密码学保密。
- scope/invocation/parent session ID、Skill 名称/版本、时间、状态、usage、工具名和 operation 等审核元数据仍按设计明文保存。
- Trace 写失败时，业务结果仍返回，只附加 warning；`traceId` 本身不证明 manifest/events/result 都存在。正式 harness 必须把缺文件或 `Trace persistence failed` 当作 harness failure。
- 进程崩溃可留下只有 manifest 或部分文件的 Trace；当前没有事务式完成标记。
- Skill 在 Trace `begin` 前加载，非法 manifest 可能根本没有 Trace。
- Trace 只存 hash，不能单独重建 invocation。正式研究必须另外冻结 task/fixture/invocation manifest。

## 6. JSON Schema 与包加载

SkillRegistry 会在加载时拒绝本地 validator 不支持的 JSON Schema 关键字，避免“manifest 声明了约束但 Runtime 静默忽略”。当前支持的是小子集，不是完整 JSON Schema。

两个语义限制需要保留：

- `enum`/`const` 使用 `Object.is`；object/array 常量不具有 JSON structural equality。现有 `analyze-evidence` 只用标量 enum，不阻塞当前 E2E。
- PARTIAL 仍须满足完整 outputSchema；若将来需要真正的部分结构，应为状态设计显式 union schema，而不是依赖 PARTIAL 名称。

`npm pack --dry-run` 成功，实际 tarball 也已解包并通过 Pi `0.84.2` DefaultResourceLoader 加载 extension 与 `analyze-evidence` Skill。发布质量仍有限：Pi 与 TypeBox peerDependencies 均写为 `*`，但只在 Pi `0.84.2` 上验证；根 README 只有 12 bytes。正式研究应锁定依赖和 tarball hash，不能把此结果外推到任意 Pi 版本。

这些问题曾在审计中被本地复现，但已由实现方修复；不能再作为冻结快照的当前 finding，也不能从历史测试通过推断未来重构不会回归。

| 问题 | 初始风险 | 冻结后的防线 |
| --- | --- | --- |
| PROJECT operation 扩大 | Broker 的 PROJECT 默认 read/list/search 可能穿透 Skill operation policy | Gateway 和 backend 双层按 allowedOperations 过滤；独立回归确认 search 工具不存在 |

| completion 抢赢 timeout/cancel | 晚到完成态可能掩盖超时、预算或父取消 | 全生命周期 timer，终止原因优先 |
| 重复 completion 与同批 provenance | 第二次 complete 或同批 read+complete 可制造含糊协议/假可见性 | first-valid-wins + duplicate fatal；同批 completion 拒绝并要求下一 turn |
| evidence 只看最终 snapshot | completion 后发生的可见性可能倒灌 | accept 前捕获 `completionResourceAudit`，并校验递归 evidence IDs |
| requestedResources 语义宽松 | 非 NEED_CONTEXT 扩权、绝对路径、越 policy operation | 状态/路径/operation/reason 矩阵 fail closed |
| 未知 JSON Schema 关键字静默忽略 | 声明边界比实际 validator 更强 | Skill 加载时拒绝未知/错位关键字 |
| child 借 ambient auth/models 配置 | 没有显式父 key 时仍可能使用环境或 credential file | 内存 credential store、`modelsPath:null`、显式 key 等值检查；OAuth/native fail closed |
| header null 删除大小写不一致 | 小写 `authorization:null` 无法删除大写旧 header | case-insensitive merge/delete 回归通过 |
| list-only 读取正文 | 列目录可引发大文件/二进制读取和未报告副作用 | 只物化名字；正文读取进入 `physicalMaterializedSet` |
| Trace 保存结果/路径原文 | prompt/result/error/path 可泄漏 | `metadata-only-v1` 对敏感值和路径做 hash/bytes 投影 |

## 8. 正式 E2E 前的阻断与准入门禁

当前没有阻止窄化 smoke 的已知源码级 blocker；仍有以下**执行级 blocker**。任一项未满足，都不应开始批量真实调用。

1. **真实父路径 preflight。** 从实际安装的 tarball 启动 Pi，明确选中 `deepseek-v4-flash`，确认 parent model 的 API 是 `openai-completions`、认证为显式 API key、不是 OAuth/native/custom stream，并完成一次最小调用。密钥只能由 Pi 认证设施提供，不能写命令行、fixture、Trace 或测试输出。
2. **两种边界 smoke。** 先跑一个 SEALED inline/file PromptRef 案例，再跑一个 exact-file BOUNDED 案例；BOUNDED 案例应强制模型先 read、下一 turn 才 complete，人工检查 evidenceRefs 和 Trace 元数据。
3. **单并发。** runner 并发固定为 1；不要依赖父工具的 parallel 声明进行研究首跑。
4. **受控 fixture。** 只用小型 UTF-8 合成文本，路径固定、无 symlink/hardlink/mount、无大文件或二进制；首个正式门禁不使用 PROJECT 或目录 read/search。
5. **Trace 完整性门禁。** Trace root 显式设在项目外；每次调用必须存在 manifest、events、result，且返回 warnings 中没有持久化失败。另保存冻结的 task/invocation manifest。
6. **独立语义验证。** 用隐藏真值和实际可见 span 验证答案/evidence claim，不把 Runtime 的资源级 visibility 当作 semantic pass。
7. **失败归因。** provider/auth/network/429/5xx 和 harness failure 单独分类，不进入模型能力失败分母；timeout/cancel 需按预注册规则重跑或排除。
8. **停止规则。** 若模型 ID/API/endpoint 漂移、一次 ambient-auth 兜底、Trace 缺失、同批 completion 被错误接受、未见资源被引用或敏感 sentinel 落盘，立即停止扩大样本。

满足以上门禁后，可以放行小规模研究 Pilot；在 Pilot 的协议稳定性、失败分布和人工 evidence 抽查完成前，不放行确认性大样本。

## 9. 仍需保留的工程限制

### 正式研究可接受但必须记录

- 目标模型由父 session 选择而非插件硬编码；runner 必须显式冻结 `deepseek-v4-flash`。
- 仅支持 API-key OpenAI-compatible chat-completions；这是 v0.1 的有意窄化。
- completion data 错误发生在 child 已终止后，Runtime 会 fail closed，不能让 child 当轮修复。
- metadata-only Trace 可审计边界与计数，但不能重建完整任务。
- 工具调用计数只计算 resource tools，不包含 completion 控制调用。

### 进入生产或扩大安全主张前必须解决

- 引入 OS/process/container 隔离，或实现 fd-relative no-follow 文件访问及明确的 hardlink/mount policy；
- 增加全局并发上限、排队/背压、active child registry、shutdown abort 和压力/泄漏测试；
- 扩展或明确版本化 provider bridge，并给 ModelRuntime/credential 生命周期提供可验证清理；
- 将 provenance 从资源级提升到 span/claim 级，或明确永远由外部 verifier 承担；
- 给 Trace 增加完成标记/恢复策略，评估 keyed hash 或每批 salt；
- 固定 peer dependency 兼容范围，补齐发布 README 和安装/升级测试。

## 11. 最终判断

SkillScope 插件已经跨过“协议原型是否可运行”的门槛，但还没有跨过“通用安全隔离产品”的门槛。最有证据支撑的下一步不是马上扩大 PROJECT 或并发，而是用 `deepseek-v4-flash` 做一个高度受控的真实 preflight，然后用单并发、小型 exact-file BOUNDED fixtures 运行探索性 Pilot。

如果该 Pilot 能证明在线模型桥稳定、completion 协议遵从率可接受、外部 span verifier 与 Trace 门禁一致，再决定是否投资更强的 FS 后端、claim-level provenance 和生产容量治理；反之，应先根据失败归因修协议，而不是用更宽资源权限掩盖问题。
